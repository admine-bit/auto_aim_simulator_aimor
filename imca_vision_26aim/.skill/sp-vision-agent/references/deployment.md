# 主机部署参考

## 区分程序职责与主机职责

应用程序只负责打开并使用已经配置好的设备。接口创建、稳定别名、权限和启动顺序等持久化工作由主机配置负责。

每个部署修复都应提供：

1. 持久化配置文件的完整内容和准确落盘路径；
2. 安装或启用命令；
3. 重启后仍然可靠的启动顺序；
4. 验证命令和预期输出；
5. 与实际配置一致的 `readme.md` 说明。

最终方案不能要求操作人员每次重启后重新手工输入命令。

## CAN 排查顺序

按以下顺序排查：

1. 确认 `can0` 存在，并检查链路状态、波特率、队列长度、错误和丢包。
2. 确认没有多个脚本或服务重复启动 `slcand`。
3. 确认 `txqueuelen` 足以支撑当前指令频率。
4. 确认应用程序没有尝试创建本应由部署系统管理的网桥或接口。
5. 在怀疑消息序列化前，检查终端电阻、适配器供电、USB 稳定性和内核日志。

将 `can0` 视为程序使用的系统前提。通过 systemd/udev 或幂等的仓库安装脚本持久化接口创建与参数调整。

## 串口与设备别名

- 使用稳定的 udev 别名，避免依赖会变化的 `/dev/ttyUSB*` 编号。
- 使用尽可能精确可靠的设备属性进行匹配：优先使用厂商/产品标识，并在可用时加入序列号。
- 明确设置用户组和权限；除非用户明确要求，否则避免把设备设为全员可写。
- 在文档中写明规则重载、设备触发、服务重启和别名验证命令。
- 确保 systemd 服务在所需设备之后启动，并能在硬件重新连接后安全恢复。

## 服务与自启动

- 将系统服务放在 `/etc/systemd/system/*.service` 或项目约定的其他持久化路径。
- 使用依赖关系和启动顺序表达前提，不添加任意时长的固定延时。
- 安装流程应可重复执行，并且不会破坏已有正确配置。
- 使用 `systemctl status`、`journalctl`、接口/设备检查和实际程序启动验证结果。
- 只有确实依赖图形用户会话的程序才使用桌面自启动。

## 文档要求

部署前提、设备别名、服务、启动命令或持久化参数发生变化时，必须更新 `readme.md`。文档要足够完整，使另一位工程人员无需查看对话记录，也能在重启后恢复到可运行状态。
